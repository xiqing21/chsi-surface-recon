# 漏洞面评估

> 本文只做**基于公开信息的可行性判断**，不含可直接对线上执行的利用代码。
> 每一项都给出：原理 → 观测证据 → 判断 → 在授权环境下怎么验。

## 一、判定方法

只看三件事：

1. 这个面**是否暴露在公网**（能连通就有攻击面，连不通就是内部面）。
2. 这个面**是否有已知的、条件匹配的漏洞类别**。
3. 打进去**能得到什么**（主数据？会话？边缘缓存？）。

学信网的核心资产是学历主数据。任何不能触达主数据的入口，价值都要打折。

---

## 二、按面逐条评估

### 2.1 CAS `service` 参数（最高优先级）

**原理**：CAS 协议里 `service` 决定票据回跳目标。若 CAS Server 未做严格白名单，可造成两类问题：

- **开放重定向**：`service=https://evil.example` → 登录后带票据跳到攻击域。
- **票据窃取**：攻击者构造 `service` 指向自己控制的页面，受害者登录后 `?ticket=ST-xxx` 落在攻击者手里，随即用该 ticket 换取会话。

**观测证据**：

```
Location: https://account.chsi.com.cn/passport/login?service=
  https%3A%2F%2Fmy.chsi.com.cn%2Farchive%2Fj_spring_cas_security_check%3Bjsessionid%3D...
```

`service` 值里直接嵌了 `;jsessionid=`，说明服务端对 `service` 的解析较宽松，至少允许 URL 含分号参数。

**判断**：这是整条链上**最值得验证**的一点。CAS 部署通常有白名单，但白名单实现常有绕过：`service=https://my.chsi.com.cn@evil.com`、`service=https://my.chsi.com.cn.evil.com`、`service=https://my.chsi.com.cn/../..//evil.com`、大小写与编码变形。

**授权环境验证点**：本地起 CAS Server，把 `service` 白名单配成 `.chsi.com.cn`，然后跑上面四种变形，看是否放行。

---

### 2.2 `rdmid` 语义（中优先级）

**原理**：`rdmid` 是服务端注入页面的 24 位随机串，随表单回传。如果它只是"防重复提交标识"而**未与验证码绑定**，那么：

- 一个 rdmid 可以配任意数量的验证码请求
- 验证码的"同一会话同一题"假设失效
- 进一步，如果验证码只校验"最近一次"，则可用大量并发 pre-fetch 提高命中

**观测证据**：页面里 `rdmid` 由服务端生成后**硬编码进 Vue 的 data()**，`imagechallenge.do?time=<ts>&rdmid=<id>` 每次刷新只换 `time`，不换 `rdmid`。这说明：**rdmid 在会话生命周期内是不变的**，它标识的是"这次查询流程"，不是"这道验证码"。

**判断**：变不变本身不算漏洞。风险在于服务端是否把 `(rdmid, yzm)` 做成一次性的原子对。如果是"按 session 存最近一次答案"，那么服务端在并发下存在竞态窗口。

**授权环境验证点**：本地复刻同一张验证码配不同 rdmid / 同一 rdmid 配多次提交，观察服务端的接受/拒绝矩阵，标出竞态窗口的位置。**不做验证码识别。**

---

### 2.3 `;jsessionid=` URL 重写（中优先级）

**原理**：容器允许 `;jsessionid=` 出现在 URL 路径里来传递会话 ID。这会带来：

- 会话 ID 出现在 URL、Referer、访问日志、代理日志里 → 泄露面扩大
- 如果 `service` 参数可被外部控制，攻击者可把自己的 jsessionid 塞进去，形成**会话固定**（Session Fixation）
- 结合 CAS，可诱发票据与会话的错配

**观测证据**：`service=https%3A%2F%2Fmy.chsi.com.cn%2Farchive%2Fj_spring_cas_security_check%3Bjsessionid%3D0A46CDF...`。这是服务端**主动**把 jsessionid 拼进回跳 URL 的，说明该机制在链路上是活的。

**判断**：Spring Security 默认有 `sessionManagement().sessionFixation().migrateSession()` 防护，但它是否对 URL 重写路径同样生效，需要实测。这是**会话固定**类问题的高发位置。

**授权环境验证点**：本地 Tomcat 开 URL 重写，复刻 CAS 回跳，测"预设 jsessionid → 登录 → 会话是否更换"。

---

### 2.4 `CHSICC01` / `CHSICC02` 自研加密 cookie（高价值，外部不可见）

**原理**：值为 `!<base64>` 格式，是典型的"服务端加密后下发、回传时解密"设计。这类自研方案的常见缺陷：

- 密钥硬编码在配置或代码里
- 加密模式用 ECB（相同明文产生相同密文，可做块重排）
- 无完整性校验（可解密任意、可篡改）
- 明文结构是 `userid|role|expire` 之类的可预测串

**观测证据**：两个子系统（`xjxl`、`job`）都用，格式一致，说明是同一套公共组件。

**判断**：**这是从外部完全无法验证的点**，只能标注为"授权后第一优先审计对象"。如果它承载的是身份/角色，一旦可伪造就等于拿到了该子系统的登录态。注意 `xjxl` 是学籍管理平台——比门户价值高得多。

**授权环境验证点**：抓样本 → 观察多份样本的密文块重合度（判断是否 ECB）→ 尝试篡改单字节看是否报错（判断有无 MAC）→ 定位加解密函数。

---

### 2.5 各子系统 ASM 策略差异（横向对比）

**观测证据**：`TS01a8fc6e`（`.xjxl`）与 `TS017de4d1`（`.job`）是**不同**的 cookie 名，证明是独立的 ASM 实例与策略。

**判断**：边缘防护强度不统一。门户（www）必然配置最严，而 `xjxl`（学籍管理平台）、`job`（就业）、`rz`（报告）、`dy`（研招）这些业务系统的策略通常是另一批人配的。**弱环在业务系统，不在门户。**

**尤其注意**：`rz.chsi.com.cn` 和 `dy.chsi.com.cn` 从当前网络到达时在 CONNECT 阶段就 503，说明它们不在常规开放面——要么是内网/专线入口，要么有更严格的地域或来源限制。这类系统往往是"以为藏起来了就没漏洞"的典型。

---

### 2.6 前端依赖（低优先级，但别忽略）

| 库 | 版本 | 已知问题 |
|---|---|---|
| jQuery | 1.9.1 | CVE-2015-9251（跨域 ajax 执行）、CVE-2019-11358（`$.extend` 原型污染）、CVE-2020-11022/11023（`htmlPrefilter` XSS） |
| Vue | 2.6.10 | EOL 无补丁；模板编译 + 未转义 sink = DOM XSS |
| iView | 4.6.1 | 组件层 XSS 历史 |

**判断**：这些库单独不存在可直接利用的 RCE。它们的作用是**放大器**——一旦站内有任何一个反射/存储 XSS 沉积点，老 jQuery 的 `htmlPrefilter` 能让 payload 绕过常见的转义。所以正确姿势是：先找输出点，再用库版本决定 payload 怎么写。

---

### 2.7 报告验证码枚举（业务逻辑面）

16 位验证码 + 报告编号。判断依据只有两条：

1. 验证码空间与随机源（是否时间/PID 派生）
2. 接口是否有频控与失败计数

`rz` 域从当前网络不可达，无法取样。若可达，测法是：连续请求 N 次记录响应差异与是否出现封禁，**不做批量枚举**。

---

### 2.8 组件漏洞类别（按需排查）

对资产表里每个目标做指纹后，按类别对号：

| 类别 | 指纹 | 排查动作 |
|---|---|---|
| Spring Actuator 未授权 | `/actuator/env`, `/env`, `/jolokia` | 直接 GET 看 200 |
| Swagger 暴露 | `/v2/api-docs`, `/swagger-ui.html` | GET 看是否返回 JSON |
| Druid 监控 | `/druid/index.html` | GET 看登录页 |
| Shiro 反序列化 | `rememberMe=deleteMe` 响应头探测 | 看是否回 `rememberMe` |
| Struts2 | `.action` 后缀 + 旧版 | 版本指纹 |
| Fastjson | 响应报错含 `fastjson` | 报错特征 |

这几类的共同点：**都是"配错了暴露在公网"而不是"零日"**。真正被打穿的绝大多数是这一类。

---

### 2.9 关于"最近的 PHP 漏洞"

明确一句：学信网的可达面全是 Java（`.action`/`.do`/`.mvc` + `JSESSIONID`）。CVE-2024-4577（php-cgi Best-Fit 编码注入）、PHP filter chain RCE 这两类，需要目标跑 PHP-CGI 且有可传参的入口。当前指纹下**不匹配**。

不是"PHP 漏洞不管用"，是"这个目标上没有 PHP"。判断漏洞能不能打的顺序永远是：先指纹 → 再对号 → 最后才是 payload。

## 三、按价值排序的行动清单（授权环境）

| 序 | 目标 | 验证内容 | 产出 |
|---|---|---|---|
| 1 | CAS `service` 校验 | 4 种白名单绕过变形 | 是否可重定向/窃票 |
| 2 | `CHSICC01/02` | 加密模式、有无 MAC | 可否伪造身份 |
| 3 | 会话固定 | `;jsessionid=` 是否被 migrate | 会话是否被固定 |
| 4 | `rdmid` 绑定 | 并发下的接受矩阵 | 竞态窗口 |
| 5 | 各子系统暴露面 | Actuator/Swagger/Druid/Shiro | 配置错误清单 |
| 6 | 输出点 | 反射/存储 XSS 沉积点 | DOM XSS 链 |

## 四、明确不会成立的方向

写清楚，省得你在错的方向上花时间：

1. **打门户改学历数据** — 主数据只读，改了也没用，且前端无写路径。
2. **PHP 系漏洞** — 目标栈里没有 PHP。
3. **想办法绕验证码去爆证书编号** — 证书编号是 17-18 位，空间不可枚举；且证书编号本身是半公开信息（毕业证上有），真正的门槛在姓名匹配。
4. **"姓名+身份证查学历"接口** — 该接口不存在。学信网零散查询要证书编号。市面上声称二要素出学历的，走的是别的通道（见 `docs/SUPPLIERS.md`）。
